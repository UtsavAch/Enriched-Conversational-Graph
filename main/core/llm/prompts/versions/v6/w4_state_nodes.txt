You maintain a running record of a project's GOALS, DECISIONS, CONSTRAINTS and
OPEN QUESTIONS as a conversation proceeds.

Given a new turn and the currently-open state nodes, emit three lists:

1. creates - new state nodes this turn brings into existence. A state node is a
   commitment that LATER turns may need to honour, check, revise or close. Most
   turns create none.
   - goal          : an overall objective the user or project is working
                     towards. A conversation usually has only one to three.
                     A single request ("help me write the script", "explain X")
                     is not a goal.
   - decision      : a choice the user makes or accepts that commits the plan,
                     settling something that could have gone another way.
                     Advice, how-to instructions and explanations are not
                     decisions unless the user adopts them as the plan.
   - constraint    : a condition the plan must satisfy, whatever else is chosen.
                     Three common kinds:
                     (a) limits: a budget, deadline, quota, capacity, size, or
                         the availability of something ("until 31 July");
                     (b) rules that apply to this project, whoever set them -
                         a policy, an instructor, a contract, documentation the
                         project must follow ("no computation on login nodes");
                     (c) requirements the design or plan must meet, usually
                         phrased with must / must not / never / only / at most
                         ("error responses must never expose stack traces").
                     Decision vs constraint: a decision picks one option ("use
                     PostgreSQL"); a constraint restricts every option ("all
                     data must stay in the EU"). When a turn adopts a
                     requirement, record it as a constraint, not a decision.
                     General knowledge that does not bind this plan ("tomatoes
                     like sun") is not a constraint.
   - open_question : a question that is STILL OPEN at the end of this turn. If
                     the same turn's answer settles it, create nothing.

2. updates - existing state nodes whose lifecycle status this turn changed.
   Valid new_status values depend on the node's type — use exactly one of these,
   never invent a status outside this list:
     goal          -> achieved (objective met) | abandoned (given up on)
     decision      -> revised (changed but still stands, can happen more than once) | reverted (undone entirely)
     constraint    -> revised (terms changed, still in force) | lifted (no longer applies)
     open_question -> resolved (answered)
   achieved, abandoned, reverted, lifted, and resolved are TERMINAL — do not
   propose an update against a node whose current status is already one of those.

3. relates - existing state nodes this turn stands in a relation to, without
   necessarily changing their status. Use exactly one of:
     supports      : reinforces the target without changing it
     contradicts   : conflicts with the target without revising or lifting it
     constrained_by: this turn's content is bound or limited by the target
     resolves      : answers/closes a target open_question
   IMPORTANT: resolves ALWAYS also produces a matching UPDATE (new_status:
   "resolved") on the same target. It is the one relation that is also a status
   change, so it appears in BOTH lists, not one or the other.
   If none of the above apply, return all three lists empty.

MERGE, DO NOT DUPLICATE. If the turn restates, refines or changes the value of
something already in the open state-node list, that is an update (revised) or a
relation on the existing node — never a new create with a similar label. A
changed number, date or choice for the same thing ("32 GB" -> "64 GB") is a
revision of the existing node. Duplicate state nodes are the main failure mode of
this task.

LABELS: one specific sentence under 15 words that names the commitment and its
key value, e.g. "Request --mem=64G for full-dataset training jobs", not
"Memory setting decided".

Note on citations: the turn's answer may contain bracketed markers like [N_2]
pointing back to an earlier interaction. Those are interaction ids, never state
node ids. Never put an N_ id in a state_node_id field.

Return strict JSON only, no preamble, no markdown fences:
{{"creates": [{{"state_type": "<goal|decision|constraint|open_question>",
              "label": "<specific label, under 15 words>"}}, ...],
  "updates": [{{"state_node_id": "<SN id from the list below>",
              "new_status": "<a status valid for that node's type>"}}, ...],
  "relates": [{{"state_node_id": "<SN id from the list below>",
              "relation": "<supports|contradicts|constrained_by|resolves>"}}, ...]}}
